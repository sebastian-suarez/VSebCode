# Phase 6: Merge of the upstream release tag 1.142.0

Executable plan for the sixth phase of the VSebCode fork: the first merge of an upstream release tag into `main`, and the procedure every later sync repeats. It is written for a fresh Claude Code session: read `CLAUDE.md` first, then this file, then work top to bottom. The facts below were measured on 2026-10-14 after `git fetch upstream --tags` and verified by the two reviews listed at the end; re-measure before acting.

## What the merge is

- `main` is upstream main `2b0c23ebbd8` (2026-10-13, version 1.143.0-dev) plus the fork's changes. The latest release tag is `1.142.0` (`d956e8a6ac5`, 2026-10-14). `release/1.142` was cut from upstream main at `c480e9e49e2` (2026-10-12), before the fork's base, so the fork already contains the 1.142 iteration; the tag adds only the 25 non-merge commits of the release branch, and 20 of them are cherry-picks whose patch is already in the base (`git cherry main 1.142.0`).
- The five remaining patches: agent host session storage compatibility (`858942da1b4`), the OpenRouter aliases of `extensions/copilot` (`35a350adf8a`), the managed plugin SDK pin of `package.json` and `remote/package.json` (`8c19d9191d3`), the MSRC security fixes (`4e706008cf7`) and the webview mixed-case authority fix (`d956e8a6ac5`). The last two are the payload for the surviving code: path containment in `src/vs/base/common/resources.ts` and `contrib/webview/browser/resourceLoading.ts`, Unicode case-insensitive comparison in `src/vs/base/common/strings.ts`, nested link sanitization of OSC 99 notifications in `terminalContrib/notification`, `terminal.integrated.allowedLinkSchemes` marked restricted, workspace trust enforced on terminal relaunch and reuse, and the webview authority fix. Upstream main received them only after the fork's base (`0695d911316`, `6750fe27325`). They touch 17 surviving paths: 15 merge on their own, `src/vs/workbench/contrib/terminal/test/common/terminalConfiguration.test.ts` is new, and `src/vs/workbench/services/workspaces/test/common/workspaceTrust.test.ts` conflicts. None of them imports a removed module.
- The same fixes shipped in `1.141.1` (2026-10-12) and `1.141.2` (the webview fix and the version bump); `1.142.0` supersedes both. Policy: each sync merges the latest release tag only.
- Dry run with directory-rename detection off (`git -c merge.directoryRenames=false merge-tree --write-tree main 1.142.0`): 145 conflicting paths and 7 clean additions. 138 conflicts are "deleted by us, modified by them" inside deleted surfaces (`contrib/chat`, `platform/agentHost`, `extensions/copilot`, `src/vs/sessions`, `contrib/mcp` and `platform/mcp`, `contrib/editTelemetry`, `platform/telemetry/common/editTelemetry.ts`, `platform/chat`, `platform/sandbox`, `platform/policy/common/copilotManagedSettings.ts` with its test, `services/policies`, `terminalContrib/chatAgentTools`, the chat component fixtures, `cli`, `.github`); 7 are "both modified": `package.json`, `remote/package.json`, both `package-lock.json`, `build/lib/policies/policyData.jsonc`, `src/vs/editor/common/textModelEditSource.ts` (upstream adds a `fusionModel` field to the chat edit source the fork deleted) and `workspaceTrust.test.ts`. Of the 7 clean additions, 6 are new files under `platform/agentHost` and `contrib/chat`; the seventh is the new terminal configuration test, which stays. With the default rename detection git additionally moves three of the new agent host files into `extensions/mermaid-markdown-features/preview-src/editor/` (the fork renamed that extension's `preview-src/chat` folder), which is why the heuristic is switched off. File renames stay detected: the fork side has 34, among them `.github/instructions/*` to `docs/guidelines/*` and the mermaid folder, so later upstream edits to the old paths flow into the new ones; nothing in `1.142.0` touches them, and every later merge reviews what arrives there.
- The header policy needs an exact base. `npm run fork-header -- <base>` flags every file that differs from `<base>`, and after the merge the fork's upstream content is neither `2b0c23ebbd8` nor `1.142.0` but their union: `1.142.0` as base would flag the 1,472 files upstream main changed between the cut and the fork's base (64 header rewrites, some losing their Microsoft line), `2b0c23ebbd8` would flag the merged files (12 rewrites). The exact base is the pure upstream merge `git merge-tree --write-tree -X theirs 2b0c23ebbd8 1.142.0` (tree `db5aa6509e8`, 60 files away from `2b0c23ebbd8`, version 1.143.0). Without `-X theirs` the two upstream sides conflict in 17 files: the 4 manifests, 9 agent host files and 4 `contrib/chat` files, all removed surfaces or manifests, so the strategy option only decides between two versions of deleted code. Simulated against the merged tree, `fork-header` with that base rewrites no merged file; 12 of the 16 non-conflicting merged files come out byte-identical to the base and the other 4 already carry the fork line with their fork patches intact.
- Two leftovers of earlier phases surfaced on the way: `src/vs/platform/actionWidget/browser/actionWidget.css` was changed by the fork in `bbd50576ccb` and still carries the Microsoft header alone, and `remote/package.json` still carries `copilotRuntimeVersion` (`CLAUDE.md` records it as removed in phase 4; nothing reads it).

## Confirm first (ask)

1. Merge `1.142.0` now, or wait for `1.143.0`? Recommendation: merge now. The tag carries security fixes the fork lacks, the delta to surviving code is small, and the procedure is best rehearsed on a small merge.
2. Keep the upstream base as a branch `upstream-base` (one signed merge commit per sync, built from the previous base and the merged tag with `git commit-tree -S`, pushed to `origin` together with `main`), or only record the tree id in `CLAUDE.md`? Recommendation: the branch. A branch survives garbage collection, `git diff upstream-base main` shows the fork's complete delta from upstream, and the header command becomes `npm run fork-header -- upstream-base` for good.
3. The phase commits on `main` (the merge commit and the follow-up commits below); nothing is pushed unless asked.
4. The OSC 99 notification sanitizer in `terminalContrib/notification/browser/terminalNotificationHandler.ts`. The one-pass regex the fork already ships backtracks quadratically (`'[x]('.repeat(40000)`, 160 KB, takes 11 s; `'['.repeat(40000) + 'x'` takes 2.5 s), upstream's MSRC fix repeats it to a fixed point and adds the nested case (`'['.repeat(n) + 'x' + '](x)'.repeat(n)` takes 2.2 s at 200 KB, 0 ms before), the handler accumulates `state.body` across sequences without a bound, and xterm accepts payloads up to 10 MB, so a program writing to the terminal can stall the renderer for as long as it likes; upstream main has no follow-up as of 2026-10-14. Options: (a) merge upstream's code unchanged and leave the behaviour to upstream; (b) merge it unchanged, then in a separate fork commit cap the title and body length before sanitizing and replace the regex with a linear scanner, with regression tests for the three inputs, carried as a fork modification, and the maintainer reports it upstream. Recommendation: (b); the merge commit stays pure either way.

## Decisions taken (2026-10-14)

The maintainer answered the confirmations above: merge `1.142.0` now and track the latest stable release tag from here on (the earlier lag came from matching VSCodium's version, which no longer applies since no VSCodium patch is used); keep the upstream base as the `upstream-base` branch; bound the sanitizer in a separate fork commit after the merge (option b); commits only, nothing is pushed; and build the removal manifest, its hygiene guard and the merge helper in this phase as its last step, extracted from this merge's resolutions, so that the next sync runs them (step 8).

## Procedure

1. Preparation. Commit this plan. On the clean `main`, run `npm run fork-header -- 2b0c23ebbd8` and commit the result separately (expected: the fork line on `actionWidget.css`, nothing else). `git fetch upstream --tags`; re-measure the facts above (`git merge-base main <tag>`, `git cherry main <tag>`, the dry run, the clean additions); the tag must be newer than the last merged one. Record `PRE=$(git rev-parse HEAD)`. Audit the two upstream sides: `git merge-tree --write-tree --name-only <previous base> <tag>` without a strategy option must list only paths inside removed surfaces, manifests, lock files or generated files; anything else means the base is built by hand in a scratch worktree.
2. Upstream base. First sync (this phase): `TREE=$(git merge-tree --write-tree -X theirs 2b0c23ebbd8 1.142.0)`, `COMMIT=$(git commit-tree -S "$TREE" -p 2b0c23ebbd8 -p 1.142.0 -m "upstream: 1.142.0 merged into 2b0c23ebbd8")`, `git branch upstream-base "$COMMIT"`; check `git diff --stat 2b0c23ebbd8 upstream-base` (60 files) against the release-branch patches. Every later sync advances the branch instead: `OLD=$(git rev-parse upstream-base)`, `TREE=$(git merge-tree --write-tree -X theirs "$OLD" <tag>)` (a non-zero exit means a modify/delete or rename conflict, which the strategy option does not resolve: stop and build the base by hand), `COMMIT=$(git commit-tree -S "$TREE" -p "$OLD" -p <tag> -m "upstream: <tag> merged")`, `git update-ref refs/heads/upstream-base "$COMMIT" "$OLD"`. `fork-header` runs only once `git merge-base --is-ancestor <tag> upstream-base` and `git merge-base --is-ancestor <tag> main` both succeed; with a stale base it would treat upstream's new files as fork additions and replace their Microsoft line.
3. Merge: `git -c merge.directoryRenames=false merge --no-ff 1.142.0`, then resolve in the index only. (a) Every "deleted by us", "added by them" and rename conflict and every clean addition under a deleted surface with `git rm`; the Status section of `CLAUDE.md` is the checklist, and a path `main` does not have is re-deleted when it belongs to a surface listed there and kept otherwise, after a look. (b) The "both modified" files hunk by hunk: an upstream hunk is dropped only when it concerns a removed surface, every other hunk is kept, and a lock-file-only update of a retained dependency is reproduced with `npm install` once the manifest is resolved; whole-file `git checkout --ours` is never the default. For `1.142.0` this was verified: the upstream hunks of `package.json`, `remote/package.json`, both lock files and `policyData.jsonc` are the Copilot SDK pins and the agent host policies deleted in phase 4, and the hunks of `textModelEditSource.ts` add a field to the deleted chat edit source, so these six files take ours whole and come out byte-identical to `main`. (c) `workspaceTrust.test.ts` has two conflict hunks and three auto-merged additions: keep the auto-merged `IFileService`, `InMemoryFileSystemProvider` and `WebSocketRemoteConnection` imports and the `IFileService` stub; from the first hunk take the `Schemas` import and not `Event` (used only by the deleted agent host tests; `noUnusedLocals` would fail); from the second hunk take only the new test "remote workspace does not inherit trust through backslash traversal" and none of the agent host tests. Commit the merge with the resolutions only (`Merge upstream release tag 1.142.0`), signed like every commit. Right after it, the invariant `diff <(git diff --name-only 2b0c23ebbd8 "$PRE") <(git diff --name-only upstream-base HEAD)` must print nothing: the set of paths the fork changes against its upstream content is the same before and after the merge, which proves the re-deletions complete, no fork change lost and the base right.
4. Follow-up commits, one each: delete `copilotRuntimeVersion` from `remote/package.json`; `npm install` (lock files; no change expected); `npm run export-policy-data -- --skip-transpile` after the build (no change expected); `npm run fork-header -- upstream-base` (no rewrite expected; any rewrite is a finding to explain); whatever `npm run typecheck-client` reports; the sanitizer adaptation if option (b) of the confirmations was chosen.
5. Validation: the phase 5 list of `CLAUDE.md` (typecheck, layers, dts, monaco, class fields, eslint and hygiene over the repository, stylelint, compile-client, cyclic dependencies, build typecheck and tests, the full Electron unit test run, the smoke start, the CLI version), plus the unit tests next to the merged files (`base/test/common/{resources,strings}.test.ts`, the terminal instance, terminal configuration, terminal notification, webview element, webview resource loading, snippets resource and workspace trust tests) and the sanitizer regression tests if (b) was chosen.
6. Reviews: a fresh-context Claude review of `git diff "$PRE" HEAD` and `/codex:adversarial-review --base "$PRE"`; findings checked against the code or a failing test; rejected findings logged in `docs/reviews/phase-6-upstream-merge-rejected.md`.
7. Close: `CLAUDE.md` (Status: a phase 6 entry with the base, the tag, the counts and the validation, and the phase 4 entry corrected for the `remote/package.json` leftover; "How to work in this fork": steps 1 to 4 with `upstream-base`; the removal plan: item 6 done, the next sync as item 7), `AGENTS.md` (the header command names `upstream-base`), and the memory notes.

8. Tooling, extracted from steps 1 to 4 once they are done, in one commit under `build/` with tests run by `cd build && npm run test`: a versioned removal manifest listing the deleted surfaces one path per line (folders and single files, the Status section of `CLAUDE.md` as the source); a hygiene check that fails when a listed path exists in the tree, so no merge can bring a surface back; and a helper `npm run upstream-merge -- <tag>` that fetches the tags, audits the two upstream sides (step 1), advances `upstream-base` (step 2), merges with `merge.directoryRenames=false`, removes every conflicted or added path that the manifest covers, and prints what is left for a human: the remaining conflicts, the clean additions outside the manifest, and the new top-level folders under `contrib`, `platform`, `services` and `extensions`, new `product.json` fields, new dependencies and new API proposals to review. "How to work in this fork" in `CLAUDE.md` then describes the sync as: run the helper, resolve what it prints, run the invariant and the validation list.

## Outcome (2026-10-14)

Executed as planned, with the review findings folded in. Commits: `cf28d5f591d` (this plan), `e94e6b7d73f` (the fork header line on `actionWidget.css`), `aa34b8fedf7` (the merge of `1.142.0`), `367805f4112` (the `copilotRuntimeVersion` leftover), `5a61389be59` (the bounded sanitizer), `8f7960df32f` (the removal manifest, the hygiene guard and `npm run upstream-merge`), then the documentation. The branch `upstream-base` is `73dd0f3e089`. The invariant held with 12,678 fork-changed paths before and after the merge, and `npm run fork-header -- upstream-base` rewrote nothing. Deviations from the plan: the sanitizer became a single-pass scanner that guarantees no parsable link remains (an exhaustive test over short texts, plus the adjacency a removal can create broken with a space), equal to upstream's result for ordinary links, instead of "a few passes then neutralize"; the manifest lists a generic folder that only became empty file by file; the helper (`build/lib/upstreamMerge.ts`) implements steps 1 to 3 and prints steps 4 and 5 for the human, and is covered by tests on temporary repositories. The validation results are in the Status section of `CLAUDE.md`.

## Reviews of the phase (2026-10-14)

Codex adversarial review of the commits (`--base e94e6b7d73f`): the scanner measured labels by original offsets and never revisited delimiters a removal makes adjacent (`[[](x)](y)` became empty, `[x][(](y)z)` kept a link), fixed by counting surviving label characters and breaking every `](` the removals leave, with the counterexamples as tests; `upstream-base` was advanced before the merge, so an aborted merge left it ahead and a retry reported an empty delta, fixed by advancing it after the merge, aborting the merge when a later step fails and reusing a base an aborted run advanced; the precommit guard rejected a staged deletion of a manifest path, fixed by checking only the paths still present. Fresh-context Claude review (Opus) of the same range: the one-pass sanitizer of the first commit let a working command link through for inputs of length 10 and more (found by enumerating every text up to length 11, 61 million inputs; the rewrite leaves no link in any of them); the 10,000-character cap did not bound the pending state (fixed by capping the pending notifications at 100, the id length at 256 and by not splitting a surrogate pair at the cut); a file upstream moves into a removed folder escaped the helper because rename detection hid the addition (fixed with `--no-renames`); the helper only counted its deletions (it now names the new upstream files it deletes, and the invariant allows for them); the manifest missed the old path of the renamed chat fixture (added); the helper should refuse other branches and print the base rollback (both done, plus literal pathspecs for `git rm`). It verified the conflict resolutions, the auto-merged files, the re-deletions, the invariant, the headers and the leftovers as correct. All findings of both reviews were verified and accepted; none rejected.
