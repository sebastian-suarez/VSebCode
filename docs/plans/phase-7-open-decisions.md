## Area A: OSC 99 notification handler (fork modification)

Findings of the phase 6 reviews in `src/vs/workbench/contrib/terminalContrib/notification/browser/terminalNotificationHandler.ts`: (a) `_showOsc99Notification` registers a `DisposableStore` for the actions and an `onDidClose` listener on the handler itself for every notification it shows or updates and never releases them, so a terminal that shows notifications grows until it is disposed (1,000 updates of one id retain 1,002 handler disposables); (b) `_osc99ActiveNotifications` keeps one entry per distinct id without limit; (c) a 10,000-character button payload splits into up to 5,000 buttons, each an `Action` and a button of the toast.

Fix (one commit, `terminal: release the disposables of closed OSC 99 notifications and cap their number and buttons`): each shown notification owns a `DisposableStore` holding its `onDidClose` listener, a `MutableDisposable` for its action store and a `MutableDisposable` for its auto-close timer; the handler keeps the active notifications, with and without id, in one insertion-ordered `Set` whose entries own those stores (no parent `DisposableStore`: a disposed child would stay in it until the handler dies), plus the id map for lookups; when a notification closes, its listener deletes the entry from the set and the map and disposes its store (the emitter tolerates a listener disposing itself); eviction walks the same set. An update of an existing id assigns a new action store to the `MutableDisposable` (which disposes the old one) and a new timer likewise, so repeated updates retain a constant number of disposables. Disposing the handler disposes the store of every remaining entry and clears the set and the maps; the notifications themselves stay open, as upstream. `MAX_OSC99_ACTIVE_NOTIFICATIONS = 100` per handler, counting notifications with and without id: when the cap is reached, the oldest active notification is closed with the new close reason `evicted`, which sends the close report if requested and no activation report. `MAX_OSC99_BUTTONS = 8`: the first eight non-empty button labels become actions.

Tests in `terminalNotification.test.ts`: the fake handle stops disposing actions itself (the production `NotificationViewItem.close()` only fires `onDidClose` and disposes its own emitters), so the suite's leak check and the assertions test the handler's ownership; the fake exposes whether it still has close listeners. Cases: a closed notification leaves no listener on its handle and its actions are disposed; 200 show, update and close cycles of one id and of anonymous notifications leave the number of live tracked disposables (a `DisposableTracker`, as in `base/test/common/lifecycle.test.ts`) at its baseline, which proves nothing stays undisposed; retention is proved behaviourally, because the tracker forgets a disposed store a collection still holds: 150 anonymous notifications shown and closed followed by 100 with ids evict nothing and the 101st evicts the first id (a closed notification still in the set would count toward the cap), and forgetting the set deletion must fail that test; disposing the handler removes the listeners and the auto-close timers of open notifications (`runWithFakedTimers` from `base/test/common/timeTravelScheduler.ts`); an update replaces the auto-close timer; the 101st notification closes the first, sends its close report without an activation report, and the alive response lists the 100 remaining ids; an update at capacity evicts nothing; anonymous notifications are evicted too; 20 buttons yield 8 actions. Docs: the "OSC 99 notifications" row of the decisions table.

## Server and web builds: options (recorded before the decision)

Inventory: `src/vs/server` (24 files: the remote extension host, whose `remoteExtensionHostAgentServer.ts` also serves the `/vscode-remote-resource` endpoint the desktop client uses for remote webview resources, and `webClientServer.ts`, which serves the web workbench; its instance is optional, the `reh` build runs without a web client, but the agent server imports its HTTP helpers `serveError`, `serveFile` and `CacheControl` for the resource endpoint and its error responses), `src/server-main.ts`, `remote/` (40 dependencies) and `remote/web/` (17), `build/gulpfile.reh.ts` (the `vscode-reh-*` and `vscode-reh-web-*` packaging) and `build/gulpfile.vscode.web.ts` (`vscode-web`, `vscode-web-min`: the static browser bundle, built by the `web` target of `build/next`, which has no server entry points), `resources/server` (18 files), `scripts/code-server.*` and `scripts/code-web.*` (the latter hosts the static bundle through `@vscode/test-web` with an in-memory folder), the web workbench entry (`workbench.web.main.ts`, `browser/web.{main,api,factory}.ts`, about 1,800 lines, `src/vs/code/browser/workbench/*`), the web-only service implementations wired in `web.main.ts`, and the product fields `serverApplicationName`, `serverDataFolderName`, `serverLicense*`, `serverGreeting`. The client-side remote machinery (`platform/remote`, `services/remote`, the resolver API, remote terminals, file system and extension management) is integrated into the desktop and stays in every option.

- A. Keep both (status quo). Remote development through third-party extensions (Open Remote SSH and the like) works only if each release publishes `vsebcode-reh-<os>-<arch>` tarballs and the extension is pointed at them; no release process exists yet. Cost: `remote/` lock files and the server and web packaging through every sync.
- B. Keep the server, drop the web workbench: delete the web entry files, `src/vs/code/browser/workbench`, `remote/web`, `build/gulpfile.vscode.web.ts`, the `reh-web` variant, `webClientServer.ts` and its routing after extracting `serveError`, `serveFile` and `CacheControl` into a server-side HTTP helper that the resource endpoint keeps using, `scripts/code-web.*`, the web smoke and API test runners and the `IWorkbenchConstructionOptions` embedder API. Remote development stays. Cost: the web-only services are not flagged by the type-check and must be found by hand; medium removal.
- C. Drop both: B plus `src/vs/server`, `src/server-main.ts`, `remote/`, `build/gulpfile.reh.ts`, `scripts/code-server.*`, `resources/server` and the server product fields. Desktop only; remote development impossible (no server matching the client commit); the smallest maintenance surface.
- D. Keep the web, drop the server: a browser-only editor from the static `vscode-web` bundle, served by any static host (or the `@vscode/test-web` dev host), with web extensions and browser file system access, without remote file systems, terminals, Node extension hosts or remote development. Everything of C's server list goes except `favicon.ico`, `manifest.json`, `code-192.png` and `code-512.png` of `resources/server`, which `build/gulpfile.vscode.web.ts` requires and which move with it; the web entry and `remote/web` stay. The bundle of the `web` target carries `workbench.web.main.internal` without the browser shell (`vs/code/browser/workbench/workbench`), so a static host needs a bootstrap page that creates the workbench from the exported factory (`@vscode/test-web` injects its own, which is why the dev host works); D therefore includes writing that page and a smoke test of the packaged bundle on a plain static host.

Recommendation: A if remote development is wanted, which then needs the tarballs in the release process; otherwise C. B only if remote development is wanted without any browser UI, since the web-only services are hard to delineate and the saving is small; D only if a hosted browser editor is a goal of the fork.
