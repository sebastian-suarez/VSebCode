# UI step 1: glass side bar

First step of the UI implementation after the v10 design (`~/Projects/VSebCode-design/VSebCode v10.dc.html`). Scope fixed by the maintainer on 2026-10-15: only the primary side bar becomes translucent; the title bar, status bar, activity bar, editor and panel cards stay opaque; the full-height side bar column of the mockup is a later layout step. The look builds on upstream's Modern UI (already default on). Setting: `window.glass`, boolean, application scope, default `true`, macOS only. Revised after the adversarial review of 2026-10-15 (see "Review").

## Facts

- Electron 43.7.7 has no Liquid Glass API (`setGlassEffect` is undefined at runtime; electron/electron#50415 was closed unmerged on 2026-06-30). It has `vibrancy` (NSVisualEffectView materials), `transparent`, `backgroundColor` with alpha and `visualEffectState`. For a transparent window its `NativeWindowMac` clears the window background, hides the standard window buttons when the title bar style is `default` (the `hidden` style keeps them through a buttons proxy) and disallows native tabbing; Electron also documents no native shadow, no transparency while DevTools is open and no click-through for transparent windows. `BrowserWindow.setBackgroundColor` paints the content view's layer, which sits behind any subview inserted there.
- macOS 27.0.1 and the Xcode 27 SDK expose `NSGlassEffectView` (`style` regular/clear, `tintColor`, `cornerRadius`; the class exists since macOS 26, `effectIsInteractive` since 27). The downloaded shell declares macOS 12 as its minimum. A throwaway N-API addon built against the Electron 43.7.7 headers loads in the shell and inserts an `NSGlassEffectView` below `ViewsCompositorSuperview` and `WebContentsViewCocoa` in the window's `BridgedContentView`; with `transparent: true` the window is non-opaque with a clear background, with only `backgroundColor: '#00000000'` it keeps the opaque window background.
- The main process repaints a live window after every splash save: `PartsSplash` saves soon after the first layout, after editor layouts, theme changes and full-screen changes, and `ThemeMainService.saveWindowSplash` calls `setBackgroundColor(colorInfo.background)` on that window.
- With Modern UI the shell background is painted on both the workbench root and `.monaco-grid-view` (`floatingPanels.css`); `AbstractPaneCompositePart.layout` subtracts the floating margins and borders from the side bar's content size; `onDidLayoutMainContainer` fires only on outer layouts, not when a sash is dragged.
- The mockup's glass side bar is `rgba(42,44,52,.6)` over `blur(40px) saturate(170%)`, with a solid `#1a1c21` fallback for reduced transparency and increased contrast; it is dark-only, has no inactive-window state, and its tint does not vary with the color theme (only the editor background does). Upstream already wires `workbench.reduceTransparency` and the OS `prefers-reduced-transparency` through `IAccessibilityService`; `nativeTheme.themeSource` follows the stored base theme, so the native material gets the right appearance.

## Spike (decides the backend; visual check by the maintainer or by captures)

Variants from `.build/electron` with the throwaway addon (`scratchpad/probe.sh <variant> hold`): `transparent` (full-window glass, native tint), `region` (glass only under a 256px column), `tint-only` (clear glass, CSS tint as in the mockup), `alpha` (transparent background color without `transparent: true`) and `vibrancy` (Electron's `sidebar` material in its own window configuration), next to the Xcode `Test` app's sidebar. Each backend passes only if every check passes: desktop visible through the side bar; traffic lights present with the hidden title bar; window shadow present; rounded corners intact; resizable by its edges; native full screen; DevTools open (documented limitation, record the behavior); inactive window; light appearance; idle CPU of the window server and renderer comparable to an opaque window. Outcome A: `NSGlassEffectView` passes and the fork ships the addon. Outcome B: only `vibrancy` passes its own list and the fork ships it behind the same contract. Outcome C: neither passes and the windows stay opaque; the step stops and the maintainer decides. Result (2026-10-15, maintainer's eyes, next to a Test app whose sidebar is a tinted `NSGlassEffectView` over a transparent window, verified through the debugger): variant `transparent` matches the reference, `alpha` stays opaque, traffic lights, shadow, corners and edge resizing are intact. Outcome A applies; full screen, DevTools, the inactive window, the light appearance and idle CPU are checked during the implementation's smoke run.

## Work

1. Native module (outcome A only): `native/glass` in the repository (`package.json` as `@vsebcode/glass`, `binding.gyp`, `src/glass.mm`, `index.js`, `index.d.ts`, fork header), a plain N-API module compiled by `npm install` through the root `.npmrc` (Electron headers, build from source) with `MACOSX_DEPLOYMENT_TARGET` matching the shell and `@available(macOS 26.0, *)` guards; exports `isSupported()`, `attach(handle, { style, tintColor, cornerRadius })`, `update(id, options)`, `detach(id)`, no-op off macOS. The root `package.json` lists it as a `file:` dependency; `build/.moduleignore` drops its sources from the package; `build/lib/dependencies.ts` must list it among the production dependencies and the packaged app must load it. The main process loads it once at startup inside a try/catch; a load failure or `isSupported() === false` disables glass for the session and logs once.
2. Main process: `window.glass` in `IWindowSettings` and the desktop configuration registration (restart prompt through `relauncher.contribution.ts`). `defaultBrowserWindowOptions` creates the main window transparent only when every gate holds: macOS, setting on, custom title bar (`!hasNativeTitlebar`), `window.nativeTabs` off, `nativeTheme.prefersReducedTransparency` false, module loaded and supported. Otherwise the window is created exactly as today. `CodeWindow` attaches the backend right after creation and records `glass: true` in `INativeWindowConfiguration` only after a successful attach. `ThemeMainService.updateBackgroundColor` leaves glass windows alone (the persisted splash colors stay opaque for non-glass launches). When the OS reduced-transparency preference flips to on, the window detaches the layer, gets the opaque theme background and reports the change over `INativeHostService`; flipping back needs a restart (creation option).
3. Renderer: `src/vs/workbench/contrib/glass/electron-browser/glass.contribution.ts` toggles the `glass` class on the main container when the window reports glass, the theme is not high contrast and `IAccessibilityService.isReducedTransparency()` is false. The compositing contract: with `.glass` the root and `.monaco-grid-view` backgrounds are transparent, and a backing element inserted below the grid paints the resolved shell color (`var(--modern-ui-shell-background, var(--vscode-modernUI-shellBackground, var(--vscode-titleBar-activeBackground)))`, the same token `floatingPanels.css` uses, so custom and inactive-window shell colors keep working) with a `clip-path: polygon(evenodd, ...)` hole equal to the side bar part's rectangle, so gutters, panels spanning the side bar column and hidden parts stay opaque. The glass side bar is square on all four corners (flush column of the mockup), so the rectangular hole matches its silhouette exactly. The rectangle comes from the side bar element's bounds, refreshed per animation frame from a `ResizeObserver` on it plus `onDidLayoutMainContainer`, `onDidChangePartVisibility`, `onDidChangePanelPosition`, `onDidChangePanelAlignment`, `onDidChangeMainEditorCenteredLayout`, side bar and activity bar position changes and zoom changes (translations without a resize included). Inside the side bar the theme backgrounds that would hide the glass are redefined for its subtree only (`--vscode-sideBar-background`, `--vscode-sideBarTitle-background`, `--vscode-sideBarSectionHeader-background`, `--vscode-sideBarStickyScroll-background` as the same `color-mix` tint), which covers the view panes, lists, trees, sticky scroll and the title painted through those variables; the part container's inline color is overridden in CSS; views moved to the panel or the secondary side bar keep their normal backgrounds. `.part.sidebar` paints the tint as `color-mix(in srgb, var(--vscode-sideBar-background) 60%, transparent)` (the maintainer's rule of 2026-10-15: the theme's side bar color at the mockup's alpha) and sits flush with the window edge like the mockup: with `.glass` the side bar loses its floating-card margin, border and radius on the window side and at the top and bottom, and the floating inset helpers of the layout service (`getFloatingPaneCompositeHorizontalMargins`, `getFloatingPaneCompositeVerticalMargins`, the outer-gutter edges), `AbstractPaneCompositePart.layout` and the splash metrics take the same glass-aware values so the content, scrollbars and the splash rectangle stay aligned in both densities and for either side bar position. Every other part keeps its opaque background; auxiliary windows are never glass.
4. Splash: the per-window `glass` flag of `INativeWindowConfiguration` is authoritative at every bootstrap and reload (the shared persisted splash only carries the translucent side bar color as a rendering hint, and the persisted background stays opaque). For a glass window `workbench.ts` injects a transparent body background instead of the opaque shell color, paints the splash root with the shell color and the same rectangular hole, and paints the side bar rectangle with the tint; without saved layout geometry, in full-screen launches or for a non-glass window the splash paints the opaque shell everywhere, so a window is never bare.
5. Tests: setting default and scope; the main-process gate for each condition (native title bar, native tabs, reduced transparency, unsupported module, load failure); the contribution's gating and the hole geometry for left and right side bars, hidden side bar and spanning panels; the glass-aware floating insets for both densities; the side bar subtree backgrounds (a populated Explorer row, the title and a sticky header read as the tint); the backing geometry after a compact-density panel move from bottom to top at unchanged height; the splash body and root for glass, non-glass, first-run and full-screen launches; two windows with the reduced-transparency preference toggled between their reloads; the splash fields; the module's argument validation and `isSupported()` under the Electron runner (skipped off macOS). Validation, in order: `npm install` (new module), `npm run compile-client`, `npm run typecheck-client`, eslint, hygiene and stylelint on the changed files, `npm run valid-layers-check`, the Electron unit suite with the new test files confirmed in the run, `./scripts/code.sh --user-data-dir .build/smoke-ud --extensions-dir .build/smoke-ext` (sash drags on both sides at 100% and 150% zoom, bottom panel spanning the side bar, full screen, reload, theme change, a second window, DevTools), and a packaged `npm run gulp vscode-darwin-arm64` build that loads the module and shows the glass.

## Status (2026-10-16)

Implemented on `main` as four commits, reviewed twice: `glass: add the native Liquid Glass module` (`native/glass`, linked as `@vsebcode/glass`; its package entry is the binary, loaded with `createRequire` because the repository forbids new JavaScript files; built with an SDK guard so an older Xcode produces a module that reports no support; the native entries hold the view weakly and the layer takes `hidden` and `appearance` options), `window: add window.glass and the native glass layer of main windows` (the window is created transparent but keeps its opaque background color until its first document loaded, then `showGlass` clears it; the glass flag of a window is the live state of its layer and reloads carry it; a closed window releases its native layer; the OS reduced-transparency preference and `workbench.reduceTransparency: on` both prevent glass windows), `workbench: render the primary side bar as glass in glass windows` (the side bar part reports its grid bounds on every layout and the layout service writes the backing's hole from them, which also follows a side bar position change; a glass toggle lays the side bar out again explicitly because the grid skips unchanged bounds; the contribution gates on high contrast and reduced transparency, tints the layer with the theme's side bar color at 60%, sets the material's appearance from the theme kind, hides the layer while the side bar is opaque and keeps the side bar opaque when the main process released the layer) and `splash: keep glass windows see-through from the first frame` (the hole only for non-high-contrast saved themes; the main process's default colors when nothing is saved). The second review round (2026-10-16) added: the explicit side bar relayout uses the grid's view size (the part's own dimension is already inset); the main process announces the loss of a layer (`onDidDetach`, forwarded as `onDidDetachGlass`) so a renderer with `workbench.reduceTransparency: off` paints opaque when the OS preference turns on; the window stays opaque until the bootstrap splash is painted and reports `vscode:revealGlass` over IPC (and is covered again before every load), with the fallback color kept in step with the theme; a hidden layer covers the window opaque again and the configuration carries `glassHidden` so a reload with reduced transparency or a high-contrast theme paints an opaque splash; the backing is a dedicated element whose hole is an inline clip path, so sash drags invalidate no inherited custom property; and the native host forwards only the option fields a caller set. The findings not acted on are logged in `docs/reviews/ui-step-1-glass-sidebar-rejected.md`.

Verified: client type check, eslint, stylelint, hygiene, layer check, the glass service, contribution and layout helper tests, the full Electron suite, the packaged macOS build (the module ships unpacked in the asar and the packaged app attaches the layer), idle CPU at 0% for a glass and an opaque instance side by side, and screen captures of the editor from sources: dark and light themes, inactive window, 144% zoom, the side bar on the right, hidden, a justified bottom panel, full screen, DevTools docked, a reload, a second window and its release on close, `workbench.reduceTransparency: on` and back, and high contrast. The maintainer confirmed on screen that the side bar is glass like the Test app, follows the sash and Cmd+B and retints on theme changes.

## Open decisions for the maintainer and the design project

- Decided on 2026-10-15: the tint is the theme's `sideBar.background` at 60% alpha, and the side bar is flush with the window edge in this step. The mockup still lacks a light appearance and an inactive-window state; the design project should specify both.
- Glass style `regular` versus `clear` (Apple reserves `clear` for media backgrounds), decided by the spike.

## Not in this step

Title bar, status bar and activity bar transparency; the full-height side bar column with the traffic lights inside it; the glass pills and pickers of the mockup (Modern UI's frosted overlays stay as they are); Windows (`backgroundMaterial`) and Linux.

## Review

Adversarial review, 2026-10-15, verdict "needs attention" on the first draft; all eight findings were verified against the pinned Electron source and this repository and changed the plan: native title bar and native tabs excluded from the gate; `updateBackgroundColor` skips glass windows; runtime support and load success gate the creation; each backend has its own pass criteria and an opaque outcome exists; the root-only gradient was replaced by the backing element with a rectangular hole covering the grid background and spanning panels; sash drags are tracked through the side bar element; the flush column was made an explicit decision because of the layout insets (decided: flush, with the insets adapted in code); the validation installs and compiles before the suite. No finding was rejected. Round two (same day) on the revised plan returned six medium findings, all verified in the code and folded in: the side bar's descendants paint the theme background through CSS variables (now redefined for the subtree); position-only layout changes need the panel position and alignment events; the rectangular hole requires a square side bar (decided with the flush column); the backing must use the live shell token, not `WORKBENCH_BACKGROUND`; the bootstrap body background must be transparent for glass windows with an opaque fallback; and the per-window attachment state, not the shared splash, decides the glass rendering at bootstrap. No finding was rejected. The raw reviews are kept in `.build/glass-spike/reviews/`.
