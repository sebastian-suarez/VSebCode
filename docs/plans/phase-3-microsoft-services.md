# Phase 3: Microsoft online services and accounts

Executable plan for the third removal phase of the VSebCode fork. It is written for a fresh session: read `CLAUDE.md` first, then this file, then work top to bottom. Every path and count was verified against the tree at the end of phase 2 (2026-10-14); re-check with `git ls-files <path>` or `git grep` before acting, because upstream merges move things. Counts are non-test `.ts` files unless stated otherwise.

## Confirm first (ask)

Two scope corrections are still waiting for the maintainer (see "Open decisions" in `CLAUDE.md`): the agent host and the agents window stay until phase 4, because 310 and about 190 files respectively couple them to the chat core. The same coupling exists for several Microsoft services: `IWorkbenchAssignmentService` (experiments) is injected by about 25 files under `src/vs/workbench/contrib/chat`, `src/vs/sessions`, `src/vs/platform/agentHost` and `src/vs/workbench/services/agentHost`; `IRemoteTunnelService` by `contrib/chat/electron-browser/{tunnelHost.contribution,toggleRemoteConnectionsActionViewItem}.ts` and `sessions/contrib/{tunnelHost,providers/remoteAgentHost}`; `IDefaultAccountService` by two chat and two sessions files; the survey editor pane by `contrib/chat/common/feedbackSurvey/chatModelFeedbackSurveyConfig.ts`; `platform/github` by chat, sessions and the agent host. Those folders are deleted in phase 4, so editing them now means editing them twice.

**Ask** the maintainer to confirm the rule this plan follows: a Microsoft service whose interface is injected by chat, sessions or agent-host code keeps its interface with a null implementation in this phase (the adopted plan already does this for `ITelemetryService`), and the interface leaves in phase 4 with its last consumers. Everything without such consumers is deleted outright. Ask at the same time for the open decisions this phase touches: updates (section 4), the Rust `cli/` with its tunnel subcommands (section 6), and whether the web and server builds stay (sections 1 and 8).

## Ground rules

- One surface per commit, mechanical deletions separate from edits to surviving code (see "How to work in this fork" in `CLAUDE.md`). The numbered sections below are the suggested commit boundaries.
- Items marked **ask** are maintainer decisions. Ask before acting on them; do not assume.
- Validation after each section that touched the named inputs:
  - anything under `src/`: `npm run typecheck-client`, then `npm run valid-layers-check` (folders were deleted), `npm run eslint -- <changed .ts files>`, and the unit tests next to the adapted code (`./scripts/test.sh --run <file>` or `npm run test-node -- --run <file>`). Remove the `eslint.config.js` import-pattern entries that name deleted folders.
  - `build/**`, `scripts/**` or `eslint.config.js`: `cd build && npm run typecheck && npm run test` (one pre-existing failure in `build/next/test/resources.test.ts` on macOS: a `/private/var` versus `/var` temp-path mismatch; anything else is new), then `npm run eslint -- <changed files>`.
  - `package.json`, `remote/package.json`, `remote/web/package.json`, `extensions/*/package.json` or `build/npm/dirs.ts`: `npm run install-fast -- --force` once at the end of the phase; the tree must stay clean afterwards.
  - Any file with a copyright header: `npm run precommit -- <files>`.
  - End of phase: `npm run compile-client`, `./scripts/code.sh --user-data-dir .build/smoke-ud --extensions-dir .build/smoke-ext` (a short path: the main-process socket path is limited to 103 characters), and `npm run gulp compile-extensions` for the extensions whose manifests changed.
