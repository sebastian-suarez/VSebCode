# UI step 1, glass side bar: review findings not acted on

The implementation review of the glass side bar step (the four commits `glass: add the native Liquid Glass module`, `window: add window.glass and the native glass layer of main windows`, `workbench: render the primary side bar as glass in glass windows` and `splash: keep glass windows see-through from the first frame`) had two fresh-context reviews on 2026-10-15: a fresh-context review of the series diff alone and an adversarial review of the series with the plan `docs/plans/ui-step-1-glass-sidebar.md`. The findings that were acted on are folded into the commits (native detach on window close and weak native references, the live glass flag of the window with the refreshed reload configuration, the explicit side bar relayout when the glass state changes, the side bar part reporting its grid bounds for the backing's hole, the hidden layer while the side bar is opaque, the appearance of the material following the theme, the `workbench.reduceTransparency: on` gate of the window creation, the opaque window until the first document loaded, the high-contrast gate and the fallback color of the splash, the stylesheet cascade and the compact card strokes, the SDK guard of the native build, the bare `module` import the test renderer can resolve, and the tests for all of it). The findings below were checked against the code or the running editor and rejected, with the evidence.

| Finding | Source | Decision and evidence |
|---|---|---|
| Exclude full screen launches from the splash hole, because the hole could use "windowed geometry saved by another window". | Adversarial review, finding 5 (part) | Rejected. The parts splash saves no layout in full screen (`partsSplash.ts`, `_shouldSaveLayoutInfo`), so upstream paints its full-screen splash from windowed geometry as well, and the splash geometry is global across windows in upstream too. The hole is measured on the splash's own side bar element, so it matches what the splash paints exactly; the first grid layout of the workbench reports the real bounds. Painting an opaque side bar card for those frames would replace a continuous glass column with an opaque flash. |
| Size the native glass view to the side bar rectangle instead of the whole content view, to reduce GPU work. | Fresh-context review, finding 4 (part) | Rejected. The renderer would have to send the rectangle to the main process on every sash-drag frame and the native view would lag the CSS hole by the IPC round trip, showing an opaque or bare-glass strip while dragging. The idle cost of the full-window layer measured 0% CPU for the glass instance and for an opaque instance side by side (five samples each with nothing else running). The layer is hidden instead whenever the renderer paints the side bar opaquely, which is the case the finding worried about. |
| "On macOS, the native window shadow will not be shown on a transparent window" (Electron docs); nothing restores the shadow. | Fresh-context review, finding 6 | Not a defect on device. The shadow is present below the glass window (capture crop of the window's bottom edge, 2026-10-15) and the maintainer confirmed traffic lights, shadow, corners and resizing in the spike. macOS derives the shadow from the window's opaque content, which the workbench provides everywhere except the side bar column. |
| Raise the tint alpha for light themes or make it contrast-driven. | Fresh-context review, finding 5 (part) | Deferred to the design project. The 60% alpha is the maintainer's rule from the v10 mockup, and the material now follows the theme's appearance (a light theme gets light glass), which was the larger part of the mismatch. The light-appearance legibility is listed among the open design questions of the plan. |
| Make the native build non-fatal for contributors with an older Xcode (optional dependency). | Fresh-context review, finding 10 (part) | The SDK guard was taken instead: with an SDK older than macOS 26 the module compiles to one that reports no support, so `npm install` never fails on it and the main process keeps its single load path. An optional dependency would make a missing module a silent runtime state that is harder to diagnose. |
| Add unit tests for the window creation path and its failure fallback. | Fresh-context review, finding 12 (part) | Not added. `CodeWindow` has no unit test harness upstream (its constructor creates a real `BrowserWindow`). The creation path is covered by the smoke runs from sources and by the packaged build, both of which log the attached layer and show the glass side bar; the failure fallback is the unchanged opaque window the service documents. |
| Gate glass windows on GPU compositing, or detach when it is lost, because transparency under software compositing is unverified. | Fresh-context review, round 2, finding 7 | Not acted on. The finding states no failure; macOS composites the window through CoreAnimation whatever the renderer's compositing mode, and the glass view is native. No software-compositing setup is at hand to test it and no report exists, so it stays an open question noted here rather than a gate that would turn glass off after a GPU process crash on a hunch. |
| Add regression tests that drive the real `Layout` and `SidebarPart` through repeated glass toggles. | Adversarial review, round 2 (next steps); fresh-context review, round 2, test gaps | Not added. The workbench `Layout` has no unit test harness upstream (it needs the real grid, parts and services), and the side bar part is constructed with a dozen services. The toggle path is covered by the pure helpers' tests and was verified on the running editor: three `workbench.reduceTransparency` cycles leave the side bar's glass column and content at the same width (window captures before and after, 2026-10-16). |
