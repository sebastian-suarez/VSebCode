# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. The rules shared by every agent (what the repository is, build and test commands, what is off limits, how to change code, the review protocol) live in `AGENTS.md`, imported above; this file holds the project knowledge base.

## What this repository is

VSebCode is a fork of `microsoft/vscode` ("Code - OSS") whose purpose is to remove everything Microsoft-specific and everything AI-specific from the editor, guided by VSCodium's patch set plus our own analysis. Upstream's engineering conventions still apply to the code that remains; the fork-specific rules below say what gets removed, how, and what is still undecided.

### Decisions already made (2026-10-14)

| Scope | Remove all four groups: the built-in AI stack including the `vscode.chat` / `vscode.lm` extension APIs; Microsoft online services (telemetry, experiments, surveys, update checks, Settings Sync, Cloud Changes, tunnels); the Microsoft/GitHub account providers and the `github` extension; Microsoft/Copilot repo tooling (`.github`, Azure Pipelines, 1ES config, agent-host build tooling). |

| Upstream tracking | Commits directly on `main`. | OSC 99 notifications | Fork-modified since phase 6: the title, body and button text a terminal notification accumulates are capped at 10,000 characters (the pending notifications at 100 and their ids at 256 characters) and markdown links are removed in one linear pass, from each field and once more from the composed message (`sanitizeOsc99MessageText` in `terminalContrib/notification`), because upstream's MSRC fix repeats a backtracking regular expression to a fixed point, which is quadratic, over unbounded text. The guarantee is that no parsable link remains (the result never contains `](` unless the text had no link); the result equals upstream's for ordinary links and for every text without one, and may keep a bracket upstream would drop in adversarial nestings. The maintainer may report it upstream. Since phase 7 each shown notification owns its disposables (the close listener, the actions, the auto-close timer) and releases them when it closes or when the handler is disposed; a terminal keeps at most 100 active notifications, closing the oldest with the close reason `evicted` (a close report if requested, no activation report; the handler sends the report and releases the notification itself when the handle's close does not fire or throws), and a notification offers at most 8 buttons. |

| Dev container schemas | `extensions/configuration-editing/schemas/devContainer.codespaces.schema.json` left in phase 7 (never referenced, excluded by `.vscodeignore`); `devContainer.vscode.schema.json` next to it is upstream's own unreferenced file and stays. |
| Completion specs | `extensions/terminal-suggest` keeps the `code`, `code-insiders`, `code-tunnel` and `code-tunnel-insiders` specs as third-party-tool completion, like `gh` and `azd`; `vsc.ts` reuses their option groups (decided in phase 7). |

## Commands

Node must match the major version in `.nvmrc` (24.x); `build/npm/preinstall.ts` refuses otherwise. `npm install` also installs the nested packages (`build/`, `extensions/`, `test/*`); the `builtInExtensions` of `product.json` are downloaded by `./scripts/code.sh` or `npm run download-builtin-extensions`, from the Marketplace now that `extensionsGallery` is set. When no dependency manifest changed, `npm install` returns early on a state hash; `npm run install-fast -- --force` runs the install scripts regardless.

| Task | Command |
|---|---|
| Install or refresh dependencies | `npm install` (first time), `npm run install-fast` (skips up-to-date installs) |
| Download Electron (version pinned in `.npmrc`) | `npm run electron`; `scripts/code.sh` and `scripts/test.sh` do it on demand |
| Client build with type-check | `npm run compile-client` |
| Incremental build, no type-check | `npm run build-fast` (two lanes, client and built-in extensions; `--client-only` skips the extensions, `--force` rebuilds everything; state lives in `.build/build-fast/state.json`) |
| Built-in extensions alone | `npm run gulp compile-extensions` |
| Watch | `npm run watch-client`, or the daemon pair `npm run watch-clientd` / `npm run kill-watch-clientd` |
| Type-check only | `npm run typecheck-client`; `cd build && npm run typecheck` for the build tooling |
| Run from sources | `./scripts/code.sh [folder]` (downloads Electron, compiles if `out/` is missing, fetches built-ins); `./scripts/code-cli.sh` |
| Lint | `npm run eslint -- <files>` (cached by content), `npm run stylelint` |
| Hygiene (copyright header, tabs, formatting) | `npm run precommit -- <files>`; with no files it checks the git index; `npm run hygiene` checks the whole repo |

`npm run compile` is the same as `compile-client`; `npm run watch` runs the client transpile, the client type-check and the extension watchers. ## Architecture

### Layers and target environments

`src/vs` is ordered `base` -> `platform` -> `editor` -> `workbench` -> `code` (Electron main process and CLI). A layer may only import from layers below it. Inside each layer, folder names fix the runtime: `common` (plain JS), `browser` (DOM), `node`, `electron-browser` (renderer with Electron IPC), `electron-utility`, `electron-main`. Both rules are enforced by the `local/code-import-patterns` ESLint rule configured in `eslint.config.js` and by `npm run valid-layers-check`.

### Only entry points load code

The workbench loads exactly what its entry files import: `src/vs/workbench/workbench.common.main.ts`, `workbench.desktop.main.ts`. A feature is a folder under `src/vs/workbench/contrib/<name>` with one `*.contribution.ts` entry point that registers services (`registerSingleton`) and workbench contributions (`src/vs/workbench/common/contributions.ts`) and is imported from one of those main files. Removing a feature therefore starts at the entry file: drop the import, delete the folder, fix what no longer compiles. Services are consumed only through constructor injection (`@IFooService`), and other contributions may use a feature only through its single `common` API file, never its internals.

### Extension API

`src/vscode-dts/vscode.d.ts` is the stable API and `vscode.proposed.<name>.d.ts` the proposals; `src/vs/platform/extensions/common/extensionsApiProposals.ts` is generated from those file names by `build/lib/apiProposalNames.ts`, so never edit it by hand. Every API area is a pair: `src/vs/workbench/api/common/extHost<X>.ts` in the extension host and `src/vs/workbench/api/browser/mainThread<X>.ts` in the renderer, connected through `extHost.protocol.ts`. Built-in extensions opt into proposals with `enabledApiProposals` in their `package.json`. Removing an API means removing the d.ts, both halves of the pair, the protocol entries and every `enabledApiProposals` reference, then running `npm run vscode-dts-compile-check`.

### product.json

`product.json` carries the product identity and every service endpoint; its shape is `IProductConfiguration` in `src/vs/base/common/product.ts`, so adding or removing a field means updating that interface. A gitignored `product.overrides.json` next to it is merged at startup by `src/bootstrap-meta.ts` and is the place for local experiments. `build/lib/builtInExtensions.ts` downloads the `builtInExtensions` list from the gallery (`extensionsGallery.serviceUrl` is set since phase 1), validated against the pinned `sha256`.

### Built-in extensions

`extensions/*` are compiled by gulp (`build/gulpfile.extensions.ts`, esbuild for webviews). The vendored Copilot Chat extension left in phase 2 and the agent host build support in phase 4; `build/lib/ripgrep.ts` keeps the platform filter for the `@vscode/ripgrep-universal` binaries that the packaging tasks apply.

### Build system

Gulp (`build/gulpfile*.ts`, invoked as `npm run gulp <task>`) orchestrates compilation, extensions, packaging (`gulpfile.vscode.{win32,linux}.ts`, `build/{win32,linux,darwin}`, `resources/`) and hygiene. The TypeScript transpile and bundle steps are esbuild in `build/next` (`build-fast`, `transpile`, `bundle`; working notes in `docs/guidelines/build-next.md`). Build scripts are TypeScript run directly by `node`, so they need no compile step. The server and standalone web packaging left in phase 7; the Rust `code` CLI (`cli/`) left in phase 3. The desktop web worker host remains. `compile-web` and `watch-web` build the built-in extensions' browser entries for development in that host; desktop packaging builds their main bundles.

## How to work in this fork

The working rules (one surface per commit, the removal order, dependency manifests, the guides to read, upstream conventions, Markdown) are in `AGENTS.md`. Fork-specific procedure:

- Syncing with upstream (procedure of phase 6): run `npm run upstream-merge -- <tag>` with the latest release tag (after `git fetch upstream --tags`, which the helper runs itself, `git tag --sort=-v:refname | grep -E '^[0-9]+\.[0-9]+\.[0-9]+$' | head -1`). The helper refuses a dirty tree or an already merged tag, audits that the previous `upstream-base` and the tag only conflict inside removed surfaces or manifests (otherwise it stops: build the base by hand in a scratch worktree), advances `upstream-base` to their `-X theirs` merge as a signed merge commit, merges the tag with `merge.directoryRenames=false` without committing, deletes again every conflicted or added path that `build/removed-surfaces.txt` covers, and prints the remaining conflicts, the additions outside the removed surfaces (keep them, or delete them and add them to the manifest) and upstream's new folders, `product.json` fields, dependencies and API proposals to review. Resolve the remaining conflicts hunk by hunk (an upstream hunk is dropped only when it concerns a removed surface; never take a whole file from one side), commit the merge with the resolutions only, then check the invariant the helper prints (the set of paths the fork changes against `upstream-base` is the same as before the merge, plus the new upstream files the helper deleted inside removed surfaces, which it lists by name), run `npm install`, `npm run fork-header -- upstream-base` (no rewrite expected), `npm run typecheck-client` (new upstream references to removed surfaces show up here and are deleted like in the phases), the validation list of the latest Status entry, and update the Status section. Upstream `main` is never merged.
- Reviews: every area of a phase gets a fresh-context review before it is committed; findings that are not acted on are logged with their evidence in `docs/reviews/<topic>-rejected.md`.
